# walkthrough — 会话接力:打包 → 新会话续上

全程假数据。演示一个不需要任何额外 skill 的习惯:一条跑了两天的长会话怎么打包成一个「接力文件」,第二天的新会话怎么接上。

**为什么要这么做**:会话越长,AI 每回一句话都要把全部历史重新过一遍——越来越慢、越来越费额度;历史太长还会被自动压缩,压缩会丢细节。一件事做完就换新会话最好,接力文件让换会话不丢东西。

**为什么不直接写进 memory**:memory 存的是长期有效的规则和教训;接力文件存的是只在未来几天有效的活状态(这单在等谁回、哪个窗口哪天到期)。活状态灌进 memory 会把它弄乱。两者各管各的。

## 背景

用户和 AI 在同一个会话里连着干了两天:整理了一批船位、给两票货报了价、在查一个定时任务为什么没出数据。会话已经被自动压缩过一次,回复开始变慢。

## 1. 打包

一件事做完的时候(不要在做到一半时),用户说——可以直接复制这段:

> 打个接力包:把这个会话的活状态写进 `contexts/HANDOFF_<今天日期_时间>.md`,固定六段——在办项(每项一行:状态 · 下一步 · 谁动 · 文件路径)、等待中的窗口、本会话关键决定(尽量用我的原话)、没回答的问题、工作树状态(未 commit / 未 push / 后台任务)、新会话第一步。只写状态和文件路径,不复制大段内容,一屏以内。打包前先检查有没有长期教训还没写进 memory,有就先写。

AI 回:

> 接力包已写好:`contexts/HANDOFF_20260115_1830.md`。另外,01-14 你说的「老龄船单独锚」是长期规则,已先写进 feedback memory。

## 2. 接力包长什么样

```markdown
# HANDOFF 2026-01-15 18:30

## 1. 在办项
- 货 A(东南亚→中国 50k 煤)· 已报 11,400–12,000 · 下一步:等货主还盘 · 谁动:等外部 · `contexts/quotes/cargo_a.md`
- 货 B(澳洲→印度 70k)· 已报价,用户说「明早看了市场再定开口」· 谁动:用户
- 船位表定时任务 0 行 · 已定位到上游字段改名,修复写好未上线 · 下一步:dry-run 验证后接回定时任务 · 谁动:AI · `tools/position_ingest/`

## 2. 等待中的窗口
- 01-16 12:00 前:货 A 货主还盘;超时则按区间下沿重报
- 货 B 失效位:同族出现 ≤{{X}} 新成交 → 重锚

## 3. 关键决定
- 01-14 用户:「老龄船一律单独锚,别混进年轻船的成交」(已写入 feedback memory)
- 01-15 用户:「定时任务修好之前,船位表先手动更新,每天中午一次」

## 4. 未回答问题
- 货 B 的佣金结构还没确认(答案会改变:报价里要不要扣除额外 1.25%)

## 5. 工作树
- branch `main` · 未 commit:`tools/position_ingest/parser.py` · 未 push:2 commits · 后台:无

## 6. 新会话第一步
先 dry-run 船位解析器修复,确认行数对得上再接回定时任务;然后看货 A 有没有还盘。
```

注意它**没有**什么:没有整段报价推导(指向 `contexts/quotes/cargo_a.md`)、没有对话流水、没有数据表原文。一屏以内,全是指针和状态。

## 3. 第二天:新会话续上

用户关掉旧会话,第二天开新会话,第一句:

> 读 `contexts/` 下最新的 HANDOFF 文件,跟现场核一遍(git 状态、文件在不在、窗口过没过期),再告诉我今天先做什么。读完在文件顶部标一行「已接力」。

AI 的动作:

1. 找 `contexts/` 下最新的 `HANDOFF_*.md` → `HANDOFF_20260115_1830.md`。
2. 看顶部有没有 `✅ 已接力` → 没有,是新包。(如果有,说明这个包已经被用过一次,先提醒用户,防止拿旧状态当新状态。)
3. 逐段读,按指针补读关键文件,**跟现场核一遍**:
   - `git status` → `parser.py` 仍未 commit ✓
   - `git log origin/main..HEAD` → 显示 0 个未 push commit ✗(包里写 2 个)
4. 报接手确认:

> 已接力(HANDOFF 01-15 18:30)。在办 3 项:
>
> 1. 船位解析器修复——今天第一件事:dry-run 验证后接回定时任务。
> 2. 货 A 等还盘,今天 12:00 是窗口。
> 3. 货 B 等你看完市场定开口;另有一个未答问题:佣金结构(影响报价是否再扣 1.25%)。
>
> 一处与包不一致:包里写 2 个 commit 未 push,现场显示已经 push 了。以现场为准——昨晚是你手动推的吗?

5. 在接力包顶部追加 `> ✅ 已接力 2026-01-16 09:05`。

最后那个问题值得问:答案会改变下一步动作——如果不是用户推的,说明有别的会话或进程在动这个仓库,得先查清楚再干活。反过来,答案不改变动作的问题就不该问。

## 4. 这个习惯换来了什么

- 用户可以放心关掉长会话——在办项、等待窗口、未答问题都不会蒸发。
- 新会话从一个干净的上下文开始:回复更快、额度更省、没有压缩丢细节的风险。
- 接手时跟现场核对,防止拿过期状态干活。

## 5. 几条容易犯的错

- 把整段对话或大段分析粘进接力文件——它应该是一屏以内的指针和状态。
- 只打包、不把长期教训写进 memory——接力文件过几天作废,教训跟着没了。
- 接手时不核现场——文件里写「未 push」,现场已经 push 了,以现场为准。
- 进度预填——「计划今晚做 X」写在下一步里,不许写成「X 已完成」。

用顺手之后,可以让 AI 把上面两段话固化成一个 skill(照 `docs/SKILL_AUTHORING.md`),以后说「接力」两个字就够了。
