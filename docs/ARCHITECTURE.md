# ARCHITECTURE.md — 整体架构与设计决策

这套架构回答一个问题:**怎么让一个「会话即生即灭」的 AI,变成有身份、有纪律、有记忆、能力会累积的长期执行幕僚。** 六层,从加载顺序讲。

```
会话启动
  │
  ▼
① CLAUDE.md 根路由器(自动加载)
  │   @import ↓
  ▼
② 身份三件套 rules/{SOUL, USER, EPISTEMICS}.md
  │
  ▼
③ 记忆三层(harness 索引自动加载;L1/L2 主动检索;L3 = rules/ 本身)
  │
  ▼
④ skill 生态(.claude/skills/ + INDEX + CLAUDE.md 硬触发区)
  │
  ▼
⑤ 自动化层(launchd/cron 夜批 + AI 夜审)
  │
  ▼
⑥ 防泄漏闸(tools/leak_scan.py,任何对外发布前)
```

## ① 根路由器:CLAUDE.md

Claude Code 每次会话自动加载它。它的职责是**路由**,不是存内容:身份 @import 进来、文件去 WORKSPACE.md 查、能力去 INDEX.md 查、纪律列成死规则。

为什么这么设计:上下文有限,根文件塞满细节会挤掉真正的工作内容;把细节下放到各自的文件,根文件只留「什么时候去读哪个文件」的路由逻辑,加载成本恒定,体系可以无限长大。

根路由器里最值钱的一块是**硬触发规则区**:「用户说某句话 → 必须走某 skill」写成不可绕过的死规则。没有这一区,AI 会在你精心设计的工作流和「随手总结一下」之间随机选择,而且多数时候选后者。

## ② 身份三件套

- `SOUL.md`——AI 是谁:身份定位(执行幕僚不是玩具)、核心信条、协作机制。
- `USER.md`——用户是谁:画像、操作身份、对 AI 的要求。
- `EPISTEMICS.md`——认知纪律:标注来源、不知道就直说、置信分级、先给反面、无新证据不让步、数据必核 asof。

为什么拆成三件而不是写成一篇:三者的变更节奏不同。EPISTEMICS 几乎不改(通用纪律);SOUL 偶尔演化(AI 自己维护);USER 随着了解加深持续更新。拆开后各自演化,互不牵连。

为什么 EPISTEMICS 是强制加载而不是「建议阅读」:谄媚和幻觉是 AI 的系统性失效,不是偶发 bug。对高杠杆决策(一单几十万的合同 / 交易 / timing),每次会话都必须带着纪律进场,靠「记得去读」是不够的。

一个实操细节:**@import 只保证「加载」,不保证「应用」**。新会话开工前逐份细读一遍,确认基线在工作状态里;长会话每 12 小时重读一遍,防身份与纪律漂移。

## ③ 记忆三层

详见 `docs/MEMORY_SYSTEM.md`。要点:

- **L3(全局约束)**:`rules/` 全部文件,每次被动加载。放「永远成立」的规则。
- **L1/L2(动态记忆)**:`contexts/memory/`,agent 需要时主动检索。放「当前状态」类易变事实。
- **harness 索引**:Claude Code 的 auto-memory,`MEMORY.md` 一行一条指针,会话开头自动加载;正文在单条记忆文件里按需打开。

为什么分层:加载成本和记忆价值不成正比。把所有记忆都自动加载,上下文很快耗尽;把所有记忆都靠检索,高频规则会被漏掉。分层的本质是按「使用频率 × 重要性」分配加载预算:铁律常驻、索引常驻、正文按需。

## ④ skill 生态

每个可复用工作流固化成 `.claude/skills/<name>/SKILL.md`:frontmatter 触发词 + MUST 触发区 + 流程 + 禁手清单 + 输出契约。规范见 `docs/SKILL_AUTHORING.md`。

为什么用 skill 而不是把流程写进 CLAUDE.md:流程是有生命周期的——会踩坑、会修订、会长出禁手清单。一个 skill 一个目录,历史教训就地沉淀(「禁手」区就是踩坑记录),而根路由器保持稳定。

skill 的死穴是「建完没人调」。两道保险:INDEX.md 一行索引(AI 查能力时能找到)+ CLAUDE.md 硬触发区(用户说触发语时必须走)。**建完不接触发点的 skill 等于不存在。**

## ⑤ 自动化层

详见 `docs/AUTOMATION.md`。三个模式:定时任务(launchd/cron)、夜批 loop(扫数据 → 计算 → 落库)、**AI 夜审**(机器产物 → 另起一个 AI 实例以 top expert 身份审 → 疑点写回 DB + 日报)。

为什么要有独立审核层:自动管道的错误是静默的——解析错一个字段、单位读错一档,落库后没人看得见,直到它污染下游判断。夜审实例与生产管道解耦,带着领域专家视角挑毛病,疑点留痕而不是静默修改。「机器算 → 专家审 → 疑点留痕」是整个自动化层的安全底座。

## ⑥ 防泄漏闸

`tools/leak_scan.py` + 你自己维护的 deny_list(不入库,见 `.gitignore`)。任何对外发布(git push 公开仓、发布网页、导出报告)前全文扫描,命中即挡。

为什么是全文扫描而不是「小心一点」:泄漏是单向门,出去就收不回。双闸模式在真实系统里验证过——白名单渲染(只有明确该去的内容进发布目录)+ 发布前全文扫描,两层都过才出门。deny_list 本身就是敏感信息(它列出了所有不能出现的名字),所以真表永不入库,仓里只放带分类注释的 example。

## 设计原则总结

1. **文件就是记忆**——一切跨会话资产落盘,目录结构即架构。
2. **加载预算分层**——常驻的越少越好,按需的路由清楚就行。
3. **纪律强制加载**——认知纪律不靠自觉。
4. **能力沉淀成 skill,踩坑沉淀成禁手**——同样的错误不犯第二次。
5. **自动化必配独立审核**——机器算,专家审,疑点留痕。
6. **对外单向门上闸**——发布前全文扫,永远。
